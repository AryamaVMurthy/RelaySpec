# RelaySpec: Frozen-Interface Emulation for Portable Speculative Proposers

**Final research proposal, implementation plan, and paper blueprint**  
**Date:** 2026-08-26  
**Status:** research-ready; one positive Qwen3-4B-to-14B systems probe exists, but the native-AR comparison and controlled 4B-to-8B ceiling experiment remain unmeasured.

---

## 1. Executive decision

The external feedback is substantially correct and changes the project in four
important ways.

First, the paper's central contribution is **not** a universal drafter. The
paper studies a narrower deployment problem: a feature-conditioned speculative
proposer has already been trained for source target `A`; a new compatible
target `B` is deployed; and retraining the proposer for `B` is undesirable.
RelaySpec keeps the old proposer and both language models frozen and trains a
small translator that makes runtime features from `B` look like the conditioning
interface that the proposer learned from `A`.

Second, multiple relays, voting, and tree construction are not the main method.
Multi-candidate and tree speculative decoding are crowded areas. Three
independent relay seeds are used first as a cheap diagnostic of **union
coverage**. A multi-relay extension is implemented only if this diagnostic
shows a large amount of complementary accepted-token coverage and a measured
cost model predicts a real end-to-end gain.

Third, proposal-aligned training is retained because it can improve the method,
but it is not claimed as a standalone novelty. Variational Speculative Decoding,
PARD-2, and related work already optimize acceptance-aware objectives. In
RelaySpec it is a specialized refinement objective for a frozen cross-target
interface adapter.

Fourth, Steering Pretrained Drafters during Speculative Decoding (SD-squared,
AAAI 2026) is the closest conceptual baseline and must be discussed directly.
It injects verifier hidden-state information into a pretrained autoregressive
drafter. RelaySpec instead emulates the **existing learned conditioning
interface** of an already feature-conditioned DFlash or EAGLE-style proposer,
keeps that proposer frozen and structurally unchanged, and removes the repeated
source-model trunk from cross-target reuse. This distinction is meaningful but
narrow; the paper is publishable only if the controlled ceiling and end-to-end
results are strong.

The final recommendation is therefore:

> Pursue RelaySpec as a frozen-interface emulation method for reusing a
> target-specific feature-conditioned proposer across larger compatible target
> models. Make Qwen3-4B DFlash to Qwen3-8B the decisive controlled experiment,
> Qwen3-4B to Qwen3-14B the scale-transfer result, and native target decoding the
> absolute speed baseline. Treat SetRelay as optional and evidence-gated.

## 2. The deployment problem

### 2.1 What exists before RelaySpec

A feature-conditioned proposer `D_A` has been trained jointly against, or from
features generated by, target model `A`. During each speculative cycle it
expects a learned condition

\[
c_t^A=I_A(h_t^A),
\]

where `h_t^A` denotes one or more hidden states of `A` and `I_A` is the native
interface used during proposer training. DFlash is the initial proposer family;
EAGLE-3 is the generality experiment.

Now a larger compatible target `B` must be served. Directly feeding `B` features
to `D_A` is usually poor because layer count, width, feature geometry, and
training-time semantics differ. The naive way to preserve the input expected by
`D_A` is to keep running model `A` alongside `B`:

1. Run `A` to produce `c_t^A`.
2. Run `D_A` to propose a block.
3. Run `B` to verify the block.
4. Commit the accepted prefix and repeat.

This can be exact, but repeated execution of `A` is pure adaptation overhead.
In the current Qwen3-4B-to-14B probe it costs about 20.45 ms per cycle.

### 2.2 What RelaySpec changes

RelaySpec observes that `B` already computes its own hidden representations
during exact verification. It learns a cheap translator

\[
R_{B\rightarrow A}:h_t^B\mapsto \widehat c_t^A
\]

that reconstructs the interface expected by the frozen proposer:

\[
\widehat c_t^A=R_{B\rightarrow A}(H_t^B),\qquad
\widehat q_t=D_A(\widehat c_t^A).
\]

Here `H_t^B` is a selected set of depth-spaced hidden states already produced
by `B`. At deployment, RelaySpec removes the repeated transformer trunk of `A`.
It does not remove the verifier and it does not transfer literal target KV
caches between incompatible layers.

### 2.3 Scope

The first paper deliberately assumes:

- compatible tokenizer, vocabulary, chat template, and special tokens;
- the proposer was trained for a smaller target in the same model family;
- the new target exposes selected hidden states during verification;
- batch-one and modest-concurrency latency are the primary regimes;
- Qwen3 is run in non-thinking mode.

Cross-tokenizer, cross-vocabulary, and one-adapter-for-all-targets claims are
out of scope. A separate translator is trained for each `(proposer, new target)`
pair.

## 3. Exact algorithm

### 3.1 Native proposer interface

For the released Qwen3-4B DFlash proposer, let the native condition be

\[
c_t^A=\operatorname{RMSNorm}\!\left(
W_D[h_t^{A,\ell_1};\ldots;h_t^{A,\ell_m}]
\right).
\]

The exact tap set is read from the official checkpoint configuration. The
current implementation runs the complete 36-layer Qwen3-4B trunk to obtain the
condition before each block proposal.

### 3.2 Relay architecture

Select `r` depth-spaced hidden states from verifier `B`:

\[
H_t^B=[h_t^{B,k_1};\ldots;h_t^{B,k_r}].
\]

The main relay is deliberately simple:

\[
\widehat c_t^A=
\operatorname{RMSNorm}\!\left(
W_2\,\sigma(W_1\operatorname{RMSNorm}(H_t^B))+W_sH_t^B
\right).
\]

`W_s` is a linear skip projection, `W_1/W_2` form a low-rank residual adapter,
and `sigma` is SiLU. A single linear projection is the small ablation. The
residual relay becomes the main architecture only if its added time yields
higher whole-request throughput.

Only relay parameters are trainable. Models `A` and `B`, the proposer `D_A`,
token embeddings, language-model heads, and all normalization parameters
outside the relay remain frozen.

### 3.3 Training stage 1: interface emulation

For matched text anchors, execute both frozen models offline and cache
`(H_t^B,c_t^A)`. Train with normalized feature reconstruction:

\[
\mathcal L_F=
\lVert\widehat c_t^A-c_t^A\rVert_2^2
+\alpha\left(1-cos(\widehat c_t^A,c_t^A)\right).
\]

Use `alpha=0.1`. This stage gives a stable warm start and directly captures the
paper's interface-emulation claim.

### 3.4 Training stage 2: frozen-proposer alignment

Feature similarity is not the deployment objective. After warm start, pass the
relayed condition through the frozen proposer and train it to assign high
probability to the continuation selected by target `B`.

For a block of length `K`, let

\[
p_k=q_{\phi,k}(y_k^B)
\]

be the frozen proposer's probability of the target continuation token at
position `k`. The main proposal-aligned surrogate is

\[
\widetilde\tau(\phi)=1+\sum_{k=1}^{K-1}
\exp\!\left(\sum_{j=1}^{k}\log(p_j+\epsilon)\right),
\]

\[
\mathcal L_P=-\log\widetilde\tau(\phi),
\qquad
\mathcal L=\lambda_F\mathcal L_F+\lambda_P\mathcal L_P.
\]

This is a lightweight differentiable approximation to expected committed
tokens. It automatically emphasizes early proposal positions because an early
failure destroys every later accepted prefix. It is not presented as a general
new acceptance-training principle; it is the inference-aligned refinement for
the frozen relay.

The mandatory objective ablation is:

1. feature reconstruction only;
2. uniform target-token cross entropy through the frozen proposer;
3. DFlash-style fixed positional weighting;
4. the prefix-survival surrogate above.

The simplest objective with the best validation tokens/s is retained. Select
from `lambda_P in {0.1, 1.0}` on one frozen 128-prompt development set. Do not
perform a large sweep.

### 3.5 Inference procedure

For each request:

1. Prefill verifier `B` and capture the selected hidden taps at the last prefix
   position.
2. Apply `R_{B->A}` to construct `c_hat_t^A`.
3. Run the frozen proposer `D_A` to generate a candidate block of `K` tokens.
4. Verify the entire block with `B` in one target forward pass.
5. Commit the longest accepted prefix plus the verifier correction token.
6. Crop rejected proposer and verifier cache entries.
7. Reuse the newly produced `B` hidden taps for the next relay condition.
8. Repeat until an end token or the generation cap.

Pseudocode:

```text
prefix, cache_B = prefill(B, prompt)
features_B = select_taps(cache_B.last_hidden_states)

while not finished(prefix):
    condition_A = relay(features_B)
    proposal, q = frozen_proposer_A(condition_A, prefix, K)
    p, new_cache_B, new_features_B = verify_block(B, proposal, cache_B)
    accepted, correction = exact_verify(proposal, q, p)
    prefix += accepted + correction
    cache_B = crop_and_commit(new_cache_B, accepted, correction)
    features_B = select_taps(new_features_B.at_committed_position)

return prefix
```

### 3.6 Exact versus approximate

The relay is approximate; the final greedy output is exact.

For greedy decoding, target `B` verifies every proposal. Only proposal tokens
equal to `B`'s native greedy tokens are committed. At the first mismatch, the
verifier token is committed. By induction over cycles, the committed prefix and
target cache equal native greedy decoding. A poor relay lowers acceptance and
speed, but cannot change the emitted greedy sequence if verification and cache
cropping are correct.

For stochastic decoding, exactness is claimed only after standard speculative
rejection sampling is implemented with the actual proposal probabilities. For
a proposed token `x`, accept with

\[
a(x)=\min\{1,p(x)/q(x)\}.
\]

On rejection, sample from normalized `(p-q)_+`. The one-step marginal is

\[
q(x)a(x)+
\left(1-\sum_v\min\{p(v),q(v)\}\right)
\frac{(p(x)-q(x))_+}{\sum_v(p(v)-q(v))_+}=p(x).
\]

Until that code path is complete and tested, the paper makes exactness claims
only for temperature-zero decoding.

## 4. Why the method can be faster

### 4.1 Complete cycle accounting

For method `m`, define cycle cost

\[
C_m=T_{\mathrm{condition},m}+T_{\mathrm{draft},m}
+T_{\mathrm{verify},m}+T_{\mathrm{commit},m}+T_{\mathrm{other},m}
\]

and mean committed tokens `tau_m`. Steady-state latency per output token is

\[
L_m=C_m/\tau_m.
\]

Naive cross-target reuse and RelaySpec have

\[
L_N=\frac{T_A+T_D+T_V+T_O}{\tau_N},
\qquad
L_R=\frac{T_R+T_D+T_V+T_O}{\tau_R}.
\]

Therefore

\[
S_{R/N}=\frac{L_N}{L_R}
=\frac{\tau_R/\tau_N}{C_R/C_N}.
\]

The relay is beneficial if and only if

\[
\boxed{\tau_R/\tau_N>C_R/C_N.}
\]

This is the paper's Amdahl gate: the retained fraction of acceptance must
exceed the retained fraction of cycle cost.

### 4.2 Current measured probe

The clean Qwen3-4B DFlash to Qwen3-14B probe contains 12 paired timing samples.
It reports:

| Quantity | Naive cross-target reuse | RelaySpec | Relative result |
|---|---:|---:|---:|
| Decode throughput | 105.768 tok/s | 131.237 tok/s | **1.2408x** |
| Latency/output token | 9.455 ms | 7.620 ms | -19.4% |
| Committed tokens/cycle | 7.067 | 6.095 | 86.24% retained |
| Approximate cycle cost | 66.815 ms | 46.440 ms | 69.51% retained |
| Conditioning path | 20.452 ms | 0.304 ms | -98.5% |
| Greedy sequence equality | reference | 12/12 | 100% in probe |

The identity predicts

\[
(0.8624)/(0.6951)=1.2408,
\]

which exactly matches the measured summary. If acceptance were unchanged, the
same measured costs imply an upper estimate of `1/0.6951 = 1.4387x` (minor
differences from earlier 1.4317x estimates arise from rounding and aggregation
details). At the measured cycle cost, RelaySpec breaks even with naive reuse at
about `7.067 x 0.6951 = 4.913` committed tokens/cycle.

This result is encouraging but incomplete:

- native Qwen3-14B autoregressive throughput was not measured;
- the probe is too small for benchmark-level confidence intervals;
- 12/12 equality is a code smoke test, not a theorem validation suite;
- there is no native Qwen3-14B DFlash ceiling;
- current feature-only training has not shown that it recovers most of a native
  target-specific proposer's acceptance.

### 4.3 Absolute speedup condition

The paper must not claim acceleration over normal inference until

\[
L_R < L_{AR}=T_B^{(1)}
\]

is measured under the same engine, precision, attention backend, prompt set,
output lengths, clocks, and GPU allocation. Relative speedup over the wasteful
cross-target baseline is useful, but absolute speedup over native AR is the
headline deployment result.

## 5. Novelty and closest prior work

### 5.1 Defensible novelty statement

The narrow claim is:

> RelaySpec makes a frozen feature-conditioned proposer trained against target
> `A` usable with compatible target `B` without changing the proposer, by
> translating `B`'s runtime hidden representation into the exact learned
> conditioning interface of `A`, thereby removing `A`'s repeated transformer
> trunk from cross-target speculative decoding.

The claim does not include inventing speculative verification, hidden-state
conditioning, multiple candidates, tree verification, or acceptance-aware
training in general.

### 5.2 Closest-work comparison

| Work | What it already establishes | Difference from RelaySpec | Required comparison |
|---|---|---|---|
| SD-squared, AAAI 2026 | Verifier hidden states can steer a pretrained AR drafter; reported acceptance gains | Modifies and fine-tunes an AR drafter with injected steering; RelaySpec emulates an existing feature interface of a frozen DFlash/EAGLE proposer and removes a source trunk | Conceptual table; implement comparable adapter if code/checkpoint permits |
| OmniDraft, NeurIPS 2025 | One generic small drafter can serve several targets | Trains a universal drafter rather than adapting a target-specific feature-conditioned proposer by interface emulation | Report scope honestly; include published speed/quality numbers only as literature context |
| PARD, ICLR 2026 and PARD-2 | Low-cost draft adaptation and acceptance-aligned optimization | Different adaptation mechanism and objective; not frozen learned-interface translation | Compare adaptation cost, parameters, data, acceptance, and speed where model pair is compatible |
| EDA, 2026 preprint | Parameter/data-efficient draft adaptation to fine-tuned targets | Adapts drafter parameters rather than keeping an existing feature-conditioned proposer unchanged | Include in related work and cost comparison |
| VSD, 2026 preprint | Sequence-acceptance-aware drafter training | RelaySpec's survival loss is a specialized relay-training surrogate, not a general first | Objective ablation; no broad novelty claim |
| MCSD, ReDrafter, MetaSD, DARTree | Multiple candidates, drafters, or trees can raise coverage | Multiple relays alone are not novel and can raise verification cost | Equal verified-node and latency budget if SetRelay is activated |
| DFlash and DFlare | Strong block-diffusion speculative proposers | RelaySpec reuses a frozen proposer across targets; it is not a better diffusion architecture | Use official checkpoints and reproduce relevant native baselines |
| EAGLE-3, NeurIPS 2025 | Strong feature-conditioned AR speculative decoding | Provides a second proposer family to test interface-emulation generality | Run only after DFlash gates pass |

### 5.3 Publishability assessment

The mechanism alone is moderately novel because SD-squared and efficient draft
adaptation are close. It becomes a credible ICLR systems-and-learning paper if
the evidence shows all of the following:

1. At least 90% of native target-specific proposer acceptance is recovered on
   the controlled Qwen3-4B-to-8B transfer.
2. Relay training consumes less than 5% of the compute required to train a
   target-specific proposer.
3. RelaySpec is measurably faster than native AR, not only faster than naive
   source-trunk reuse.
4. The gain persists on Qwen3-14B and at least one second proposer family.
5. Greedy exactness, full component timing, memory, serving throughput, and
   confidence intervals are all reported.

If it only achieves the current 1.24x relative gain over naive reuse while
failing to beat native AR, the result is a useful engineering note rather than
an ICLR main-paper result.

## 6. Optional multi-relay extension

### 6.1 Diagnostic before implementation

Train three relays with identical data and architecture but independent seeds.
On the same frozen prompts, record:

- acceptance of each relay;
- candidate-token overlap at each block position;
- per-position correctness union;
- oracle best-of-three accepted prefix, computed offline;
- relay and proposer time for one versus three paths.

The important event at block position `k` is

\[
\Pr\left(\bigcup_{m=1}^{M}E_{m,k}\right),
\]

where `E_{m,k}` means relay `m` includes the correct target continuation through
position `k`. Majority agreement is not the objective. Three identical wrong
proposals have high agreement and zero benefit.

### 6.2 Activation gate

Do not build a tree unless both conditions pass:

1. oracle best-of-three increases mean committed tokens by at least 1.0 token
   per cycle over the best single relay; and
2. the measured cost model predicts at least 5% additional end-to-end
   throughput.

For single and multi-relay modes, throughput improves only if

\[
\tau_M/\tau_1>C_M/C_1.
\]

If the single relay commits 6.1 tokens/cycle and the oracle commits only 6.3,
the extension is dropped. If oracle coverage exceeds about 7.1-8.0 at small
draft cost, a constrained union tree is justified.

### 6.3 Fair evaluation if activated

Compare against one-proposer multi-candidate sampling and DARTree under:

- equal total verified nodes per cycle;
- equal maximum proposal depth;
- equal target verification implementation;
- measured construction and memory cost;
- identical prompts and decoding settings.

SetRelay is an optional secondary contribution, never required for the main
RelaySpec paper.

## 7. Research questions and claims

### RQ1: Can interface emulation recover a native proposer's proposal quality?

Primary evidence: Qwen3-4B DFlash proposer transferred to Qwen3-8B, compared
with official target-specific Qwen3-8B DFlash.

Success: at least 90% of native proposer acceptance and at least 80% of its
speedup over AR, using less than 5% of its training compute.

### RQ2: Does source-trunk removal improve whole-request performance?

Primary evidence: source-trunk timing, relay timing, cycle cost, acceptance,
tokens/s, end-to-end latency, and the measured-versus-predicted Amdahl identity.

Success: at least 1.15x over naive cross-target reuse and at least 1.15x over
native AR on the controlled pair.

### RQ3: Does it scale to a larger target without a native proposer?

Primary evidence: Qwen3-4B DFlash to Qwen3-14B on math, code, and chat.

Success: at least 1.20x over naive reuse, at least 1.10x over native AR, and a
positive paired gain in every category.

### RQ4: Is the principle proposer-agnostic within its stated scope?

Primary evidence: Qwen3-4B EAGLE-3 to Qwen3-8B and Qwen3-14B, each with its own
relay.

Success: at least 1.10x over the corresponding naive source-trunk reuse and no
loss of decoding exactness.

### RQ5: Is relay diversity useful after paying verification cost?

Primary evidence: three-seed oracle union probe, followed by an equal-budget
tree benchmark only if activated.

Success: at least 5% measured throughput above the best single relay. Otherwise
the result stays as a short analysis and the main method remains single-relay.

## 8. Experimental matrix

### 8.1 Model pairs

Every training and benchmark job must expose exactly four GPUs. Batch-one jobs
run four independent paired streams, one per GPU, and aggregate raw request
records.

| ID | Frozen proposer trained for | New verifier | Role |
|---|---|---|---|
| D-8 | Qwen3-4B DFlash, block 16 | Qwen3-8B | Killer controlled experiment with native 8B DFlash ceiling |
| D-14 | Qwen3-4B DFlash, block 16 | Qwen3-14B | Headline scale transfer and current probe |
| E-8 | Qwen3-4B EAGLE-3 | Qwen3-8B | Controlled second-proposer test |
| E-14 | Qwen3-4B EAGLE-3 | Qwen3-14B | Generality at headline target scale |

Do not add additional model families until D-8 and D-14 pass. If resources
remain, one second-family target pair may be added as supplementary evidence,
but it must have compatible vocabulary and a reproducible proposer checkpoint.

### 8.2 Required method rows

1. **Native AR-B:** target only, exact greedy decoding.
2. **Native proposer-B:** official target-specific DFlash/EAGLE checkpoint,
   available for the 8B controlled pair.
3. **Direct reuse:** feed unadapted B features to A's proposer wherever shapes
   permit; an accuracy/acceptance diagnostic, not necessarily a viable system.
4. **Naive A-to-B reuse:** run A's source trunk, frozen proposer A, and target B.
5. **Relay-F:** interface reconstruction only.
6. **Relay-P:** feature warm start plus best frozen-proposer-aligned objective;
   intended main method.
7. **Small target-specific adapter:** train the closest parameter-budget draft
   adaptation baseline if an official implementation supports the pair.
8. **SD-squared-style steering:** closest hidden-state adaptation baseline if
   reproducible for the selected AR proposer; otherwise provide a careful
   non-empirical comparison and do not fabricate results.
9. **SetRelay:** only after the activation gate.

### 8.3 Training data

Use target-generated, non-thinking continuations from a decontaminated
Open-PerfectBlend-style mixture:

| Scale | Examples | Composition | Maximum length |
|---|---:|---|---:|
| Probe | 1,024 | 50% math, 25% code, 25% chat | 1,024 |
| Main-small | 4,096 | same | 1,024 |
| Main-medium | 16,384 | same | 1,024 |

The target model generates the training continuations so the relay is aligned
to the verifier actually used at inference. Sample block anchors instead of
applying a loss at every token. Remove exact duplicates and any example sharing
a 32-token substring with evaluation prompts. Save source dataset IDs,
generation parameters, target revision, hashes, and decontamination logs.

The existing 4K MATH-only checkpoint remains a domain-specialized ablation. It
is not the main checkpoint for code or chat.

### 8.4 Evaluation suite

The primary suite follows recent DFlash/EAGLE-style math, code, and chat
evaluation while keeping total cost bounded.

| Category | Benchmark | Size | Output cap | Primary quality metric |
|---|---|---:|---:|---|
| Math | MATH-500 | 500 | 2,048 | official exact-answer accuracy |
| Math | GSM8K | fixed 200 | 2,048 | exact-answer accuracy |
| Code | HumanEval | 164 | 2,048 | pass@1 |
| Code | MBPP | fixed 200 | 2,048 | pass@1 |
| Chat | MT-Bench | 80 | 2,048 | native-token equality, speed, output length |

AIME is excluded. All Qwen3 runs use the official chat template with thinking
disabled. Temperature zero is the main table. Judge-based chat scoring is run
once on native outputs, because exact speculative methods emit identical text.

### 8.5 Regime sweeps

Use 64 fixed prompts for a controlled grid:

- prompt lengths: 128, 512, 2,048, 8,192 tokens;
- requested output lengths: 128, 512, 2,048 tokens;
- block sizes: 8, 16, 32;
- serving concurrency: 1, 4, 8, 16 across the fixed four-GPU node.

The length grid identifies where the removed source trunk is a material
fraction of total latency. The concurrency grid tests whether target
verification, rather than the removed trunk, becomes dominant at higher batch.

## 9. Measurements and statistical protocol

### 9.1 Every request record

Record:

- prompt ID, benchmark, method, model/checkpoint revisions, seed;
- prompt tokens, generated tokens, stop reason, cap-hit status;
- end-to-end request time, prefill time, decode time, time to first token;
- output tok/s, inter-token latency, verification cycles;
- accepted tokens at every cycle and block position;
- native source conditioning time or relay time;
- proposer time, verifier time, logit-head time, cache-crop/commit time;
- synchronization and unattributed time;
- peak allocated/reserved memory and GPU utilization;
- output-token hash and native-target equality flag.

### 9.2 Aggregate metrics

Primary:

- geometric-mean speedup over native AR;
- geometric-mean speedup over naive reuse;
- mean committed tokens/cycle;
- fraction of native target-specific proposer acceptance recovered;
- official task accuracy/pass@1;
- training GPU-hours and percentage of target-specific proposer training;
- peak memory and checkpoint size.

Secondary:

- TTFT, p50/p95 request latency, throughput at concurrency;
- acceptance survival curve by block position;
- relay feature error by target depth and token type;
- predicted versus measured speedup residual;
- energy per output token if reliable power telemetry is available.

### 9.3 Timing discipline

- two untimed warmups before every timed group;
- five timed repetitions for microbenchmarks;
- alternate method order within each prompt;
- synchronize only at defined timing boundaries;
- use CUDA events for GPU regions and monotonic wall time for requests;
- lock engine, precision, attention backend, prompt manifest, caps, and GPU
  clocks within a comparison;
- store raw JSONL before aggregation;
- require profiled regions to explain at least 95% of wall time.

Report paired-bootstrap 95% confidence intervals over prompts, preserving
within-prompt method pairing. For three final relay seeds on D-8 and D-14,
report seed mean and range as well as the paired interval.

## 10. Minimal ablation set

Each ablation tests one paper claim.

1. **Training objective:** feature-only, uniform CE, fixed positional CE,
   prefix-survival surrogate.
2. **Data scale:** 1K, 4K, 16K mixed examples.
3. **Feature taps:** final layer; three depth-spaced taps; five depth-spaced
   taps.
4. **Relay capacity:** linear; low-rank residual relay.
5. **Block size:** 8, 16, 32 with full cycle cost and throughput.
6. **System removal:** native AR; naive full source trunk; relay with source
   model still loaded; relay with unnecessary source weights unloaded.
7. **Scale:** D-8 versus D-14.
8. **Proposer family:** DFlash versus EAGLE-3.
9. **Regime:** prompt/output lengths and serving concurrency.
10. **Exactness:** greedy token equality; stochastic exactness only after the
    rejection sampler passes unit and distribution tests.
11. **Relay diversity diagnostic:** three independent seeds, overlap, and
    oracle union—no tree unless its gate passes.

Do not run broad activation, optimizer, decomposition, or architecture sweeps.
The purpose is a clear causal paper, not a search report.

## 11. Decision gates

### Gate 0: measurement validity

Run native Qwen3-8B and Qwen3-14B AR first.

Pass if:

- repeated throughput coefficient of variation is below 3%;
- timed regions explain at least 95% of request time;
- 64/64 greedy outputs of verified methods equal native target outputs;
- mismatch-at-first, mismatch-in-middle, and full-accept cache tests pass.

### Gate 1: controlled D-8 ceiling

Train Relay-F and Relay-P on 4K mixed examples and compare with native 8B
DFlash.

Pass if Relay-P:

- recovers at least 90% of native 8B DFlash acceptance;
- uses less than 5% of its reported/reproduced training compute;
- is at least 1.15x faster than native AR;
- is at least 1.15x faster than naive cross-target reuse;
- retains exact greedy output.

This is the decisive scientific gate. If it fails, fix interface selection and
training before running large benchmark suites.

### Gate 2: D-14 scale result

On 64 prompts balanced across math, code, and chat, pass if:

- at least 1.20x faster than naive reuse;
- at least 1.10x faster than native AR;
- positive paired gain in every category;
- relay below 1 ms/cycle;
- exact greedy equality on every prompt.

### Gate 3: multi-relay activation

Pass only if three independent seeds show:

- oracle best-of-three at least +1.0 committed token/cycle over the best single;
- cost-model prediction of at least +5% throughput;
- materially non-identical candidate coverage.

If it fails, omit SetRelay from the main method.

### Gate 4: proposer generality

E-8 and E-14 each must exceed naive EAGLE source-trunk reuse by at least 1.10x
without exactness loss. If this fails, frame RelaySpec specifically as frozen
block-diffusion proposer reuse.

### Gate 5: paper-ready evidence

Proceed to the main paper only if:

- lower 95% confidence bound of Relay-P versus native AR exceeds 1.0 on every
  full benchmark;
- geometric-mean native-AR speedup is at least 1.15x;
- geometric-mean gain over naive reuse is at least 1.15x;
- D-8 acceptance recovery is at least 90%;
- training compute is below 5% of a target-specific proposer;
- all main-table outputs are exact under greedy decoding.

## 14. Paper structure

### Proposed title

**RelaySpec: Reusing Frozen Feature-Conditioned Proposers Across Language Model
Targets by Interface Emulation**

### Abstract claim template

Feature-conditioned speculative proposers achieve strong acceptance but are
tightly coupled to the target representations used during training. Naive
reuse on a new target must execute the old source model to reconstruct this
condition, eroding end-to-end speed. RelaySpec learns a small representation
translator from hidden states already computed by the new verifier to the
frozen proposer's original interface. Exact target verification preserves
greedy outputs, while a frozen-proposer-aligned refinement recovers acceptance.
The final abstract fills in measured acceptance recovery, native-AR speedup,
training compute, model pairs, and serving results only after all gates pass.

### Main contributions

1. Identify target-interface coupling as the hidden systems cost of reusing
   feature-conditioned speculative proposers across compatible targets.
2. Introduce frozen-interface emulation: a small per-target relay that replaces
   the repeated source transformer without modifying the proposer or verifier.
3. Derive and validate the Amdahl condition linking cycle-cost reduction and
   acceptance retention, with complete measured component accounting.
4. Show data- and compute-efficient adaptation across target scales and, if
   Gate 4 passes, across DFlash and EAGLE-3 proposer families.
5. Optionally show that independent relay uncertainty yields useful candidate
   union coverage, only if Gate 3 produces a measured end-to-end gain.

### Required main tables

1. **Core D-8/D-14 result:** quality, acceptance, tok/s, native-AR speedup,
   naive-reuse speedup, memory.
2. **Controlled ceiling and adaptation cost:** native 8B proposer versus Relay-P,
   data, trainable parameters, GPU-hours, acceptance recovered.
3. **Ablations:** objective, taps, relay capacity, data scale, block size.
4. **Generality:** E-8/E-14 if Gate 4 passes.
5. **Serving:** concurrency throughput, p50/p95 latency, memory.

### Required figures

1. System diagram contrasting native target proposer, naive cross-target reuse,
   and RelaySpec.
2. Cycle-time waterfall showing the removed source trunk.
3. Predicted versus measured speedup from
   `(tau_R/tau_N)/(C_R/C_N)`.
4. Acceptance survival curve by block position.
5. Data/compute versus acceptance-recovery Pareto plot.
6. Prompt/output-length speedup heatmap.
7. Optional relay-union plot only if Gate 3 activates SetRelay.

### Appendix obligations

- exact greedy proof and cache invariant;
- stochastic proof and distribution tests when implemented;
- complete hyperparameters and model revisions;
- dataset generation and decontamination procedure;
- all benchmark prompt manifests;
- raw timing schema and bootstrap procedure;
- complete component profiles and negative gate outcomes needed for
  reproducibility, even though the main narrative stays focused on positive
  passing configurations.
