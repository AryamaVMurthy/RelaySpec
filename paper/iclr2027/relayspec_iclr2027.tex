\begin{abstract}
Feature-conditioned speculative drafters are trained around the hidden
states of a particular language model. RelaySpec reuses these drafters
with a new target by learning a linear conditioning interface while
keeping the prediction network frozen and removing the source transformer
from generation. Across DFlash and EAGLE-3 retargeted from Qwen3-4B to 8B
and 14B, the original fits achieve 2.35--5.11 times autoregressive
throughput on MATH-500. Frozen-checkpoint tests show that 512 calibration
examples retain 97.5\% and 98.9\% of the throughput obtained with 2,048
examples on 256 GSM8K questions. A richer generated-rollout recipe reaches
native DFlash throughput, exceeding it by 2.6\% in two matched 128-request
NuminaMath runs. Controlled capacity, optimization and adaptation studies
support a low-cost dense interface while showing that better feature
fitting does not consistently accelerate decoding. Separate Llama and
cross-tokenizer Qwen-to-Llama transfers reach 2.52 and 2.75 times matched
FP32-target AR throughput, with exact token agreement on all 128 requests
per transfer. Expanded calibration improves cross-family throughput by
14.3\% but leaves Llama-to-Llama throughput essentially unchanged.
These findings establish practical operating points for inherited
drafters and characterize the data, capacity and numerical limits of
interface-only adaptation.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

A deployment may inherit a speculative drafter trained for one language
model but need to serve another: a larger model, a smaller model, or one
from a different family. Feature-conditioned drafters such as DFlash and
EAGLE-3 rely on the original model's internal states
\citep{chen2026dflash,li2025eagle3}. Keeping that \emph{source} model
supplies compatible features but retains another transformer in the
generation loop. Training a new drafter incurs a different adaptation
cost. We ask how much of the inherited drafter can be reused by changing
only its conditioning interface.

RelaySpec learns a linear map from a new \emph{target}'s hidden states
to the context consumed by the frozen drafter. During calibration,
source and target process shared text to provide paired supervision.
During generation, verification already computes the target states
needed for the next draft. The map converts them into the drafter's
input, allowing the source transformer to be removed. The target,
drafter, inherited embedding and vocabulary projection remain fixed.
The target verifier continues to decide which tokens are committed
\citep{leviathan2023speculative}.

The central idea is to adapt the conditioning interface while retaining
the drafter's trained prediction weights. Its value depends on whether
proposal quality survives the changed inputs well enough to offset the
removed source computation. Matched AR, native-drafter and source-reuse
controls measure this tradeoff across both drafter families and expose
code workloads where retaining the source is faster.

\paragraph{Contributions and main findings.}
\label{sec:contributions}
\begin{enumerate}
\item \textbf{Retarget a frozen drafter through its input interface.}
RelaySpec replaces source conditioning with mapped target features,
removing the source transformer while preserving the drafter's prediction
weights and target-controlled verification. We implement this in DFlash
and EAGLE-3 (Section~\ref{sec:method}).
\item \textbf{Establish a useful regime for simple calibration.}
On frozen GSM8K tests, 512 examples retain 97.5\% and 98.9\% of
2,048-example throughput. Dense maps lead the completed 8B capacity
comparisons, despite testing MLPs, longer fits and regularization.
Better feature fitting need not produce faster decoding
(Section~\ref{sec:controlled-scaling}).
\item \textbf{Show that inherited drafters can reach native throughput.}
A richer linear recipe using 16,384 generated rollouts exceeds native
DFlash throughput by 2.6\% in two matched runs, with 128/128 exact AR
sequences. This establishes a higher-effort calibration option
(Section~\ref{sec:rollout-extension}).
\item \textbf{Demonstrate reuse across model sizes and tokenizers.}
Llama-to-Llama and Qwen-to-Llama transfers reach $2.52\times$ and
$2.75\times$ matched FP32-target AR throughput, with 128/128 exact
sequences per pair. Expanded calibration helps the cross-family recipe
but leaves the Llama comparison unchanged within uncertainty
(Section~\ref{sec:family-extension}).
\end{enumerate}

\section{Related work and positioning}
\label{sec:related}

\paragraph{Retargeting an inherited drafter.}
DFlash and EAGLE-3 condition their proposals on target features
\citep{chen2026dflash,li2025eagle3}, tying an inherited drafter to its
training interface. TriSpec already supports adapter-only finetuning
into a fixed EAGLE-family drafter, mapping proxy features to the
expected feature space \citep{jiang2026trispec}. Adapter-only tuning
is therefore not our novelty claim. TriSpec uses a proxy to approve
some tokens without full-target verification. RelaySpec instead removes
the source transformer from generation, retargets its inherited drafter
to a new verifier, and retains target-controlled acceptance. Our
contribution is this deployment setting and its measured data,
capacity and source-removal behavior across two drafting families.

\paragraph{Target-independent drafting and dynamic steering.}
PARD adapts an autoregressive draft model for parallel token prediction
and reuses it across a target family \citep{an2026pard}. Thus reuse across
targets is established prior work. Its target-independent drafter offers
zero additional target-specific fitting at deployment. RelaySpec instead
makes a small target-specific investment to reuse a feature-conditioned
checkpoint and exploit the new target's internal states. SD$^2$ is a
closer alignment alternative: it computes steering from verifier states
and injects it into a pretrained drafter \citep{berdoz2026sd2}.
Our fitted input map replaces source conditioning, whereas SD$^2$
learns steering within the drafter. The experiments include its public
frozen-drafter configuration and PARD's released checkpoint, with their
own matched AR controls (Appendix~\ref{app:externalbaselines}). These
comparisons expose practical alternatives without attributing differences
in runtime or inherited models to the alignment mechanism alone.

\paragraph{Distillation and drafter adaptation.}
OmniDraft uses online hybrid distillation and an n-gram cache to address
cross-vocabulary deployment \citep{ramakrishnan2025omnidraft}.
Our primary study uses a shared vocabulary. A separate Qwen-to-Llama
extension aligns shared text boundaries during fitting and translates
proposals between tokenizers before target verification
(Section~\ref{sec:family-extension}). It tests one heterogeneous pair,
not a general cross-vocabulary sampling scheme
\citep{timor2025heterogeneous}. RepSpec changes draft training through
structural re-parameterization \citep{huo2026repspec}. VSD optimizes
sequence acceptance, and the Draft-OPD preprint studies on-policy
teacher feedback \citep{zou2026vsd,lei2026draftopd}. These approaches
improve a drafter's learned prediction behavior. RelaySpec freezes the
prediction weights and regresses their input context. Our matched warm-budget connector-CE and rank-32 LoRA comparisons
test this alternative locally (Table~\ref{tab:adaptation-main}), without
ranking untested objectives or full-drafter training.

\paragraph{Frozen interfaces and the meaning of feature alignment.}
Adapters, low-rank updates and model stitching already adapt or connect
frozen networks \citep{houlsby2019adapters,hu2022lora,bansal2021stitching}.
EDSD selects two target feature layers using representation metrics while
co-designing drafter architecture and training \citep{cheng2026edsd}.
Our native-interface studies instead reduce and recalibrate the input
projection of a released drafter whose prediction network stays fixed.
Successful stitching need not imply equivalent information
\citep{smith2025stitching}. We therefore evaluate decoded speed and quality alongside feature
error, using matched-capacity maps and frozen-checkpoint confirmation.

\paragraph{Proposal structure and execution.}
Tree policies, prediction heads and execution scheduling improve different
parts of speculative decoding \citep{cai2024medusa,li2024eagle2,wang2025opttree,miao2024specinfer,kumar2026ssd}.
Self-speculative methods reuse parts of the target
\citep{zhang2024draftverify,elhoushi2024layerskip}. RelaySpec instead
changes the conditioning path of an inherited drafter. Its compatibility
with other scheduling policies is not established by our experiments.

\section{Preliminaries}
\label{sec:preliminaries}
\subsection{Drafting and target verification}
An autoregressive model generates one token at a time. Blockwise and
speculative methods propose several tokens, then check them in a target
pass \citep{stern2018blockwise,xia2023specdec,leviathan2023speculative}.
In greedy decoding, the verifier commits the longest matching prefix
and a target-selected next token. RelaySpec preserves this decoder and
changes the features supplied to its drafter.

\subsection{Throughput and accepted progress}
\label{sec:cost}

Our primary metric is end-to-end output throughput: total generated tokens
divided by total request time, including prompt processing. Let $T_A$,
$T_R$ and $T_N$ denote this throughput for plain AR, RelaySpec and the
native target-specific drafter. We report
\begin{equation}
\text{AR speedup}=T_R/T_A,\qquad
\text{native throughput retained}=100\,T_R/T_N\ \%.
\label{eq:metrics}
\end{equation}
Throughput includes prompt processing. We also report summed AR time
relative to summed relay time because output lengths can differ.
Accepted progress counts tokens advanced per verification cycle,
including the target-supplied token. Removing source computation saves
cycle time but can reduce accepted progress. Appendix~\ref{app:acceptance}
specifies this tradeoff and the position-wise acceptance convention.

\section{Method}
\label{sec:method}

\subsection{Fit the input consumed by the frozen drafter}
We run the source and new target on the same text and collect hidden
states after five selected transformer blocks. Concatenating these states
gives the target vector $h_t$ and source vector $s_t$ at position $t$.
The drafter's frozen projection $F$ converts source features to its input
width. We learn a bias-free matrix $W$ that supplies this input from $h_t$.
Figure~\ref{fig:fit} separates fitting from generation.

\begin{figure}[H]
\centering
\includegraphics[width=.90\linewidth]{figures/retargeting_workflow.pdf}
\caption{Fit once, then reuse the frozen drafter. The source and target
process identical text during fitting. Only the map is updated. During
generation, target features from committed positions feed the next draft.}
\label{fig:fit}
\end{figure}

DFlash consumes normalized projected features, while EAGLE-3 consumes
the raw projection. Let $N_{\rm in}$ be fixed RMS normalization
\citep{zhang2019rmsnorm} and $N_{\rm out}$ the released output normalization.
Teacher and mapped contexts are
\begin{equation}
\begin{aligned}
\text{DFlash:}\quad c_t&=N_{\rm out}(Fs_t), &
\widehat c_t&=N_{\rm out}(WN_{\rm in}(h_t)),\\
\text{EAGLE-3:}\quad c_t&=Fs_t, &\widehat c_t&=Wh_t.
\end{aligned}
\label{eq:interfaces}
\end{equation}
We fit $W$ by minimizing the squared context error relative to the teacher's
squared magnitude. For a record with $n$ token positions,
\begin{equation}
\mathcal L(W)=\frac1n\sum_{t=1}^{n}
\frac{\|\widehat c_t-c_t\|_2^2}{\max(\|c_t\|_2^2,\epsilon)}.
\label{eq:loss}
\end{equation}
We average token losses within records and records across workers,
with $\epsilon$ the smallest positive normal FP32 value. Teacher-magnitude
normalization prevents larger vectors from dominating. The normalized
DFlash objective differs from raw linear least squares.
The original fits use 4,096 math problem-and-solution conversations,
capped at 192 tokens. Supervision is the source context vector.
Only $W$ is updated, with 52.43M/65.54M weights for 8B/14B targets.
Appendix~\ref{app:protocol} gives dimensions, layers and fitting settings.

\paragraph{A richer linear calibration recipe.}
We also fit separate per-layer maps $W_i$ with a layer-alignment term
in addition to context regression:
\begin{equation}
\mathcal L_{\rm layer+context}
=\mathcal L_{\rm context}
+\frac{1}{5n}\sum_{t,i}
\frac{\|W_i h_{t,i}-s_{t,i}\|_2^2}{\|s_{t,i}\|_2^2+10^{-6}}.
\label{eq:layer-context}
\end{equation}
Here $\widehat c_t=N_{\rm out}(F\operatorname{concat}_i W_i h_{t,i})$,
and the context term uses the same additive $10^{-6}$ denominator.
The two terms have equal weight. These maps take raw inputs and fold
into one projection before inference. Thus both recipes retain a linear
interface, but their input normalization and supervision differ.
The generated-rollout experiment in Section~\ref{sec:rollout-extension}
tests the complete richer recipe, not an isolated loss ablation.


\subsection{Draft with the new target's features}
The target caches prompt states, and the map supplies the frozen
drafter's context. The target verifies proposals in parallel, commits
the matching prefix plus its next token, and crops the cache to the
committed prefix. Mapped states feed the next cycle (Figure~\ref{fig:verify}).

The standard greedy equivalence argument requires block verification to
return the same token choices as single-token evaluation of each identical
prefix \citep{leviathan2023speculative}. Finite-precision implementations
can change those choices. We therefore measure task accuracy and token
agreement separately from throughput. The map itself never supplies the
scores used for target verification.

\section{Experiments}
\subsection{Experimental setup}
\label{sec:setup}

\paragraph{Models and runtime.}
The primary suite retargets the released Qwen3-4B DFlash and DeepSpec EAGLE-3 drafters to
Qwen3-8B and Qwen3-14B \citep{yang2025qwen3,deepspec2026software}.
DFlash uses block length 16, EAGLE-3 a seven-position chain. Native
controls use released target-specific drafters in the same implementation.
Four L40S GPUs each process one sequential request per worker. Historical
block and memory studies use RTX 6000 Ada. Within-run methods share
hardware. These are single-request measurements, not batched serving
\citep{kwon2023pagedattention,zheng2024sglang}. Table~\ref{tab:setup} gives
the primary protocol. Extensions specify separate runtimes and AR controls.

\paragraph{Workloads and data use.}
We evaluate math, code and conversation workloads because speculative
speed varies across tasks \citep{xia2024specbench,abramovich2026speedbench}.
MATH-500 supplies 500 questions \citep{lightman2023verify}. The breadth suite contains 128 GSM8K
questions, 164 HumanEval tasks, 378 MBPP tasks and 80 two-turn MT-Bench
conversations \citep{hendrycks2021math,cobbe2021gsm8k,chen2021humaneval,austin2021mbpp,zheng2023mtbench}.
The 32-question development set informed interface and loss choices.
Historical evaluations retain this exposure history. Fitting and evaluation
problem texts have zero normalized exact matches. Appendix~\ref{app:data}
quantifies related templates using token overlap. All completed workload
cells in each reported suite are included. Extended calibration uses
NuminaMath-CoT \citep{li2024numinamath}.

\paragraph{Controlled scaling protocol.}
Original 4,096-record maps remain fixed across the broad evaluation.
Additional sweeps vary records, capacity and updates using shared frozen
features and 1,024 validation records. The longer-output 8B comparisons
use 128 exposed MATH questions with a 2,048-token cap. Initial 14B and
adaptation screens use sixteen questions at 256 tokens, followed by
32 GSM8K questions at 2,048 tokens for 14B. These development studies
remain separate from the broad evaluation.

\paragraph{Quality and pairing.}
We score the primary MATH-500 outputs used for the AR timing comparison with the
pinned Qwen math scorer. Historical code comparisons use EvalPlus base
and expanded tests \citep{liu2023evalplus}. MT-Bench measures two-turn
generation time, with each method conditioning its second turn on its own
first answer. Its bootstrap unit is the conversation. Other confidence
intervals resample matched requests and condition on the fitted checkpoint.
Model loading and external task scoring sit outside the request timer.

RelaySpec accelerates all four primary MATH-500 configurations
(Figure~\ref{fig:primary}a). DFlash reaches 186.49 and 116.88 tokens/s at
8B and 14B, while EAGLE-3 reaches 84.92 and 59.18. AR-relative ratios
span 2.35--5.11, with all paired intervals above one.

\paragraph{Speed across workloads.}

RelaySpec is 1.85--3.69 times faster than AR across all eight DFlash breadth
cells (Appendix Figure~\ref{fig:breadth}). At 14B, code remains faster than
AR even where source reuse beats the relay. AR measures acceleration,
while source reuse measures the benefit of removing its source.



\paragraph{Fitting work and deployment memory.}

The 52.43--65.54M-weight maps fit in 85.6--118.5 seconds on four RTX 6000
Ada GPUs, including feature computation and optimization after loading.
Source removal saves 7.80/7.63 GiB in separate EAGLE-3 8B/14B processes.
Required source embeddings and vocabulary projections remain resident.
Appendix~\ref{app:cost} reports absolute memory and separate setup costs.

\subsection{Calibration cost and interface capacity}
\label{sec:ablations}

\subsubsection{How much data and mapper capacity are needed?}
\label{sec:controlled-scaling}

Holding 8,192 batch-four updates fixed separates distinct records from
optimization work. Throughput rises from 96.9 tokens/s with 16 records
to 192.8 with 512, then ranges from 196.9 to 198.4 at 2,048--32,768
(Figure~\ref{fig:scaling}a). Thus 16 records give $2.58\times$ AR, and
512 retain 97.2\% of the observed best. All eleven maps score 105/128.
These single-seed development results do not establish a general data
threshold. Appendix~\ref{app:design} retains the historical MATH-only study.

\paragraph{Better feature fitting need not mean faster decoding.}
The 94.37M-parameter MLP-4096 at $N=2048$ reaches 190.15 tokens/s,
below dense (Figure~\ref{fig:scaling}b). Extending the width-512 MLP from 8,192 to 32,768 updates
on the same 2,048 records raises throughput only from 154.39 to 157.68.
Regularization gives no matched endpoint benefit from L2 and only
small weight-decay gains in feature validation. Dense mapping leads
both completed 8B long-output capacity comparisons, including
matched-parameter nonlinear alternatives. This is a ranking of the
tested recipes, not an optimized function-class comparison.
Appendix Figure~\ref{fig:loss-speed} relates both fitting losses to decoding.

\paragraph{What the interface reveals.}
The 14B full-answer development screen repeats the dense/MLP ordering,
while lower-rate EAGLE-3 follow-ups show sensitivity to optimization
(Appendix~\ref{app:target14-capacity}). Selecting two feature layers cuts
projection weights by 60\% and retains 97.6\% retargeted DFlash throughput.
Separate native DFlash and EAGLE-3 projections retain 97.1\% and 98.8\%
throughput on frozen GSM8K tests. Code can require a third layer
(Appendix~\ref{app:interface-compression}). Mixed math/instruction fitting
improves code and chat speed but slightly lowers math speed at two seeds
(Appendix~\ref{app:composition}). These findings make interface design a
useful control over reuse, while limiting claims of a single best recipe.

\subsection{Reaching native throughput with richer calibration}
\label{sec:rollout-extension}

We train
Equation~\ref{eq:layer-context} on 16,384 generated NuminaMath rollouts \citep{li2024numinamath}
for three epochs, then evaluate 128 requests from a separate NuminaMath
split in a batch-invariant BF16 runtime. RelaySpec reaches 167.83 and
167.97 tokens/s in two runs, versus 163.57 and 163.67 for a native
Qwen3-8B DFlash drafter. Reversing GPU assignments preserves the 2.6\%
advantage (Figure~\ref{fig:extensions}b). AR, native and relay outputs
match on all 128 requests in both runs. AR is measured once and reused.
Thus reusing a 4B drafter need not impose a native-throughput deficit
in this fitted recipe and runtime.



This recipe costs more: rollout generation takes 96.4 minutes on two
GPUs, feature capture and validation 52.0 minutes on two, and mapper
epoch computation 14.4 minutes on one. The model and data preparation costs are not part of the
original 86--119-second fitting claim. Data, loss, optimization and
runtime all change, so this result does not identify which change caused
the gain (Appendix~\ref{app:rollout-extension}).

\subsection{Beyond Qwen scaling: new families and tokenizers}
\label{sec:family-extension}

We reuse a Llama-3.1-8B DFlash drafter with Llama-3.2-3B, and a
Qwen3-4B DFlash drafter with Llama-3.1-8B
\citep{grattafiori2024llama3,meta2024llama32}. For different tokenizers,
fitting pairs hidden states at shared text-prefix endpoints. Generation
converts source proposals into target token IDs, which the target then
verifies. Only proposed input and conditioning change, not commit authority.

We freeze checkpoints and block lengths after development, then evaluate
128 additional MATH questions at a 2,048-token cap. Targets and maps use
FP32 with TF32 disabled, while frozen drafters use BF16. Both old and
selected maps match their matched FP32 AR on all 128 requests in each
pair (Figure~\ref{fig:extensions}a). The selected cross-family map raises
end-to-end throughput by 14.3\% [11.5,17.2]\%, reaching $2.75\times$ AR.
The larger Llama map changes throughput by only 0.45\% [-0.63,1.54]\%.
More calibration work helps the tested cross-family recipe, but the
within-family result favors retaining its cheaper original map.

\section{Discussion and limitations}
\label{sec:limitations}
\paragraph{Main insights.}
A drafter's learned prediction function can remain useful after its
conditioning model changes. A small linear interface often suffices,
but its feature error alone does not determine speed. Richer fitting
reaches native throughput in one setting and helps cross-family reuse,
while the larger Llama fit adds no resolved gain. Interface selection
therefore needs both feature and decoding measurements.

\paragraph{Scope and limitations.}
Mechanism comparisons hold drafter and runtime fixed, while public
baselines differ in runtime and training history. Historical BF16 and
later exact matches require their respective numerical references.
Frozen small-data tests support speed retention, not tight accuracy
noninferiority. Coverage remains limited to the evaluated pairs, one
cross-tokenizer transfer and one request per worker. Development exposure,
related templates, few fitting seeds and capped outputs limit generalization.
The rollout recipe changes data, supervision and optimization together.

\section{Conclusion}
\label{sec:scope}
RelaySpec makes a frozen drafter's conditioning interface a practical
unit of adaptation. Calibrated reuse removes the source transformer and
supports both small-data efficiency and native-level throughput in a
tested richer recipe.

\paragraph{Features and dimensions.}
Layer indices count transformer blocks from zero. Source and Qwen3-8B
states come from blocks $[1,9,17,25,33]$. Qwen3-14B states come from

8B input. Joining five 5,120-wide states gives a 25,600-wide 14B input.
Both drafter interfaces have width 2,560. The matrix dimensions are
therefore $2,560\times20,480$ and $2,560\times25,600$.
The DFlash input normalization has no trainable gain or bias. The
released output normalization remains frozen.

\paragraph{Training.}
Four workers average record losses at each update. Seed 1729 fixes the
selected fit. AdamW uses learning rate 0.0006, zero weight decay and
gradient clipping at 1.0. Computation uses BF16, with the feature loss
computed in FP32. Each of 1,024 updates processes four records, each
capped at 192 rendered tokens. The same map remains fixed across tasks.

\paragraph{Runtime and timing.}
The main AR runs use Python 3.12.13 and PyTorch 2.9.1 with CUDA 12.8.
DFlash uses Transformers 5.3.0. EAGLE-3 uses the pinned 5.10.2 overlay.
Each worker owns a full target replica on one L40S GPU. Four workers
process independent requests rather than splitting one model over GPUs.
One warmup per method precedes measured requests. Method order rotates
across requests. The synchronized timer includes prompt processing,
drafting, verification, feature updates and runtime bookkeeping.
The historical block and memory experiments use RTX 6000 Ada GPUs.

\paragraph{Compression should account for the feature distribution.}
At matched rank 1,024, approximating the mapper's weight matrix alone
can be much weaker than preserving its observed projection outputs
(Table~\ref{tab:compression-objective}). For the latter, we sample up to
eight feature positions from each of 512 fitting records, approximate
the dominant uncentered output subspace $U_k$ of $XW^\top$, and deploy
$U_k(U_k^\top W)$, using normalized inputs in $X$ where the mapper
requires them. This is an application of data-aware compression,
with established precedents in ASVD and SVD-LLM
\citep{yuan2023asvd,wang2025svdllm}, not a new general factorization method.
EAGLE-3 illustrates the distinction: weight-only SVD retains 54.1\%
on GSM8K, output-subspace compression 93.9\%, and direct teacher fitting
96.1\%. On MATH the latter two are nearly tied. Direct fitting remains
useful alongside posthoc compression.

\paragraph{Retargeting toward a smaller verifier.}
\label{app:downscale}
As a boundary experiment, we reuse the Qwen3-4B DFlash drafter with
Qwen3-0.6B, taking target layers [1,7,13,19,25]. The source and target
tokenizer files are byte-identical at the pinned revisions. We extract
512 fitting and 128 validation records and fit for 8,192 updates.
Two dense seeds use 13.11M mapper parameters. Factored linear and GELU
MLP maps at width 1,024 each use 7.86M. Per-worker fitting takes
54--61 seconds after cache extraction, which takes 32.8 seconds on
four GPUs including model loading.

On 16 development GSM8K requests, dense RelaySpec reaches 168.0 tokens/s,
or 3.26 times AR [3.00,3.50], compared with 102.6 tokens/s for source
reuse (Table~\ref{tab:downscale}). The second seed repeats the result.
AR time divided by RelaySpec time is 3.32 [3.07,3.55]. We report both
ratios because outputs differ from AR on nine questions in this BF16
run. All methods finish below the 512-token cap. Correctness is 10/16
for speculative methods and 9/16 for AR, with a conservative paired
accuracy-difference interval of $[-23.9,33.8]$ percentage points for
dense RelaySpec. This does not establish accuracy superiority or
noninferiority.

Source verification occupies 46.8\% of source-reuse request time.
RelaySpec removes it while reducing progress per cycle from 5.45 to
4.61. This supports the source-removal mechanism even when the verifier
is smaller than the drafter's source model. It remains a small,
single-workload development result rather than a confirmed deployment
recommendation for small verifiers.

To investigate the output disagreement, we repeat the same sixteen
questions with the same fitted checkpoint in BF16 and full FP32.
All source, draft, target and mapper computations change precision
together, and FP32 disables TF32. Within-precision AR agreement is
7/16 in BF16 and 16/16 in FP32. The BF16 and FP32 AR outputs themselves
match on only 5/16 questions. This intervention supports a numerical
explanation in this sample, but also changes kernel dispatch and does
not isolate target precision alone. It is not a proof of agreement on
other prompts. The four diagnostic workers complete in 61--78 seconds.
Numerical sensitivity and FP32 mitigation have prior study, including
LayerCast \citep{yuan2025numerical}. Our contribution here is a controlled
diagnostic of the inherited-drafter interface, not discovery of this
numerical phenomenon or a new precision algorithm.

The pattern extends to the tested code and dialogue screens
(Table~\ref{tab:precision-breadth}). Code agreement rises from 5/8 to
8/8, and dialogue agreement from 8/16 to 16/16 timed turns across eight
conversations. Each precision has its own AR baseline. Code outputs are
not execution-scored, and dialogue responses have no quality scores.
The results support applicability beyond math in this small verifier,
while distinguishing token agreement from task performance.

\paragraph{Selecting target features.}
\label{app:interface-compression}
The interface also permits a controlled test of target-layer sufficiency.

keeping the released drafter frozen, the same 512 fitting records and
8,192 batch-four updates. This reduces the mapper from 52.43M to
20.97M parameters. It does not remove target-model layers or reduce
whole-model parameters by 60\%. Initial development screens selected
this two-layer interface before confirmation.

a 2,048-token cap, and a 95\% throughput-retention criterion. An updated

\section{Acceptance and numerical agreement}
\label{app:acceptance}

A retention value of 90\% means the reused drafter produces 90\% as many
tokens per second as the target's own drafter. It is not the fraction of
speedup above AR. We also report the ratio of summed AR request time to
summed relay request time. This differs from a throughput ratio when
output lengths differ.

Acceptance explains how speed is obtained. We report the pooled number
of tokens advanced per proposal-verification cycle, including the
implementation's target-supplied progress. This is distinct from the
fraction of proposed draft tokens accepted. Appendix~\ref{app:acceptance}
gives the position-wise curves and precise counting convention.

Let $c_R$ be the average relay cycle time and $a_R$ its average progress.
Its decode time per output token is approximately $c_R/a_R$.
If $c_A$ is AR time per token, then the decode-only approximation is
\begin{equation}
\text{AR-relative decode speed}\ \approx\ \frac{a_R c_A}{c_R}.
\label{eq:cycle}
\end{equation}
Removing source conditioning reduces cycle cost. Imperfect feature
matching may reduce progress. The map is useful when the saved computation
outweighs the extra cycles. We measure end-to-end speed directly and use
this approximation to interpret the component measurements.

We pool all recorded proposal cycles rather than averaging each request's
mean. This weights cycles equally. DFlash's recorded length is one
already target-selected position plus the accepted draft prefix.
EAGLE-3's length follows its shared decoder's progress count. These
quantities measure work advanced per cycle, including target-supplied
progress. A proposed-token acceptance fraction requires separating those
positions and accounting for the number proposed.

\label{app:rollout-extension}

This study instantiates Equation~\ref{eq:layer-context} with a larger
calibration corpus and a batch-invariant inference runtime. It is a
separate operating point from the original short-conversation fitting
recipe. The source is Qwen3-4B and the target is Qwen3-8B. The inherited
4B DFlash drafter, target, source fusion, normalization, embedding and
vocabulary head remain frozen. The five bias-free maps have
$2560\times4096$ weights each, totaling 52,428,800 trainable parameters.
Their block-output taps are [1,9,17,25,33], using zero-based indices.

\paragraph{Data and supervision.}
We use the pinned NuminaMath-CoT source shard and a custom split, not
MATH-500. Normalized question text is grouped after replacing numbers
and punctuation, retaining one representative per group. Deterministic
source-proportional sampling yields 16,384 training, 256 development
and 4,096 evaluation records. Evaluation uses the first 128 records of
that evaluation split. These checks prevent exact and defined-template
group overlap within this corpus, but do not establish semantic
independence from pretraining or other project data.
The frozen target generates training solutions with a 4,096-output-token
cap. Both frozen models then process the same complete token sequences.
Segment-stratified sampling retains 25\% of positions, giving 5,398,695
positions per epoch. Each record has equal total loss weight.

\paragraph{Objective and optimization.}
For a selected position, let $z=\operatorname{concat}_i W_i h_i$.
The layer term averages five relative squared errors, and the context
term compares $N_{\rm out}(Fz)$ with $N_{\rm out}(Fs)$, both with the
additive denominator constant $10^{-6}$. The source normalization is
\begin{equation}
N_{\rm out}(u)=\gamma\odot u
\left(\frac{1}{2560}\sum_j u_j^2+10^{-6}\right)^{-1/2},
\end{equation}
with frozen $\gamma$. Unlike Equation~\ref{eq:interfaces}'s direct-context
DFlash map, the per-layer maps receive raw inputs. Folding produces
$W_{\rm fold}=[F_1W_1,\ldots,F_5W_5]$, so inference still uses one
linear projection followed by the inherited output normalization.
The layer and context terms have equal coefficients. No cross-entropy,
KL divergence or acceptance-rate objective is used.

Xavier initialization uses seed 42. AdamW has peak learning rate $10^{-3}$,
zero weight decay, 5\% warmup and cosine decay. Batches contain 2,048
positions and gradient norm is clipped at one. Three fixed epochs yield
7,911 updates, with no validation-based checkpoint selection. Epoch
losses are 0.738, 0.330 and 0.240. Their measured computation times are
281.1, 293.1 and 290.7 seconds. BF16 folded-export relative context error
is $2.15\times10^{-5}$ under the recorded export check.
Rollout generation, feature capture and validation, and fitting are
separate stages. Their times are 96.4 minutes on two GPUs, 52.0 minutes
on two GPUs and 14.4 minutes on one GPU, respectively.

\paragraph{Inference and repeat.}
All arms use vLLM 0.28, BF16 and batch-invariant execution on L40S GPUs,
greedy decoding with thinking disabled, no prefix caching and one measured
request per worker. The 128 outputs contain 124,899 tokens per arm, with
104 ordinary stops and 24 length stops at 2,048 tokens. Timers include
prefill and generation, excluding model setup and four warmups. Requests
that trigger new compilation have one warmed repeat, with cold timings
retained in the record. The second speculative run reverses GPU assignments
and reuses the original AR measurement. All prompt IDs, generated token
arrays and finish reasons agree across AR, native and relay, and across
both speculative runs. Table~\ref{tab:rollout-transfer} reports both runs
rather than selecting the faster one.

This experiment follows the supplied archived training, mapper, export
and benchmark implementation on newly generated rollouts. All historical
rollout shard hashes differ, and the fitted weights differ as well.
The execution therefore reproduces the specified recipe and measured
behavior on a new data realization, not the original training tensors.
Capture uses eager batch-invariant execution after compiled capture
failed the recorded sampled/dense feature check. The corrected capture
passes that check without relaxing its tolerance. These details and the
complete source/configuration fingerprints accompany the result artifacts.

The 2.6\% native-throughput advantage has a paired request interval above
parity in both runs, conditional on one fitted checkpoint. The comparison
changes inherited drafter release, and does not equate native drafter
training costs. There is no matched normalized-dense fit on these same
generated rollouts. Consequently it does not isolate the benefit of
layer supervision, more data, longer answers or the runtime change.

FP32 floor. Its fitting input RMS epsilon is $10^{-6}$, while deployment
preserves the existing target input epsilon $10^{-5}$. The output epsilon
is $10^{-6}$. A fixed-feature comparison over 256 validation records and
8,192 positions per pair measures mean context relative MSE of
$5.14\times10^{-7}$ and $5.49\times10^{-7}$ from this epsilon difference.
The runtime and weights were not changed after selection. This diagnostic
quantifies a recipe discrepancy and does not remove it.

The layer-plus-context alternatives do not beat the selected dense recipe
in development. This does not conflict with the native-parity rollout
result, which changes the training text, position sampling and runtime.
The two studies do not establish a globally optimal loss. Full fitting
trajectories and all measured candidates remain in the accompanying
campaign record.

\paragraph{Final 128-question protocol.}
We shuffle the pinned MATH-500 records with seed 1729 and take indices
40 through 167, excluding the 40 used in recent family development and
checks. Both pairs receive the same 128 questions, with a 2,048-output-token
cap. These are additional questions for this campaign, not globally unseen
records in the broader project. Four GPUs execute independent requests
in sixteen waves, two workers per pair. Every worker shares the frozen
models and one AR reference between original and selected maps, rotating
method order. Each mapper has exactly 128 unique requests. Token arrays
are saved outside the request timer, checked against their hashes and
compared directly. All four mapper arms agree with AR on 128/128 sequences.
The within-family outputs total 62,608 tokens, with eight cap stops.
Cross-family outputs total 92,610 tokens, with 24 cap stops.

Target and mapper weights, target head and target computation are FP32,
with TF32 disabled. The frozen drafter, source embedding/head and mapped
context are BF16. The source transformer is unloaded after retaining
required vocabulary tensors. The matched AR reference uses the same FP32
target. End-to-end throughput includes prompt processing and generation,
while excluding model loading, tokenization and final text decoding.
Decode-only rates are 116.00/116.52 tokens/s for original/selected Llama
maps and 52.29/59.83 for the cross-family maps. Main-paper values include
prefill. Paired 95\% intervals use 10,000 request resamples with seed 1729,
conditioning on the selected checkpoint and runtime.

The original-to-selected request-throughput ratios are 1.0045
[0.9937,1.0154] for Llama and 1.1432 [1.1155,1.1723] for cross-family.
The Llama interval includes parity, favoring retention of the cheaper
original mapper. Cross-family tuning yields a measured improvement,
without isolating data count from optimization. No independent fitting-seed
replication is included in this final comparison.

\paragraph{Verification work and request heterogeneity.}
The selected cross-family map is faster on 122/128 requests. Total verifier
calls fall from 28,000 to 24,487, increasing final target tokens per call
from 3.31 to 3.78. For Llama, only 58/128 requests improve and calls change
from 16,066 to 16,094, leaving progress at about 3.90. This accounts for
the direction of the aggregate contrast without isolating data count as

\paragraph{Numerical agreement and its limits.}
Earlier BF16 target runs matched AR on only 4/8 within-family and 0/8
cross-family pilot requests for both old and layer-plus-context maps.
Replaying identical prefixes exposed target-score differences across
execution shapes and cache histories. FP32 target execution improved
agreement in the recorded diagnostics without changing the acceptance
rule, and the expanded mixed-precision configuration matches on all 128
requests here. These results do not validate earlier BF16 output streams
or prove agreement on untested inputs. Exact sequence equality is an
implementation check, not mathematical answer correctness. In the new
comparisons, each mapper necessarily inherits the matched AR answers and
its cap-related truncation on the tested prompts.

\section{Additional related work}
\label{app:additionalrelated}
\paragraph{Improving drafting.}
EAGLE predicts future features with shifted tokens \citep{li2024eagle}.
EAGLE-3 combines feature layers and simulated drafting steps
\citep{li2025eagle3}. DFlash predicts a block in parallel
\citep{chen2026dflash}, while Medusa uses several prediction heads
\citep{cai2024medusa}. GRIFFIN addresses training-to-decoding token
alignment \citep{hu2025griffin}. RepSpec changes the training structure
\citep{huo2026repspec}, while VSD and Draft-OPD optimize accepted
proposals \citep{zou2026vsd,lei2026draftopd}. RelaySpec inherits the
trained drafter and changes only its conditioning input.

\paragraph{Proposal structure and execution.}
EAGLE-2 and OPT-Tree adapt proposal trees
\citep{li2024eagle2,wang2025opttree}. SpecInfer organizes tree verification
\citep{miao2024specinfer}. Distributed speculative inference and
speculative speculative decoding overlap computation
\citep{timor2025dsi,kumar2026ssd}. Draft \& Verify skips target layers
\citep{zhang2024draftverify}, LayerSkip trains early exits
\citep{elhoushi2024layerskip}, and Lookahead checks candidates without an
auxiliary drafter \citep{fu2024lookahead}. RelaySpec retains an external
drafter and holds its released proposal structure fixed. We evaluate the
cost and accepted progress of changing its feature source.
